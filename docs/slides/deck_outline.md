## 1. Title: Which clone differences break an agent?
- Clone Fidelity Auditor: compares a clone with the real site
- One ticket per difference, with screenshots from both sites
- Validated on a self-hosted reference site

**Asset:** none (title slide)

**Speaker notes:** Frist trains agents in clones. Today we check fidelity by eye. This talk covers what the tool finds, how we validated it, and what it can and can't tell you about agent performance.

## 2. The problem
- A clone that looks right can teach the wrong site
- Renamed labels, dead buttons, moved click targets
- Today: checked by eye

**Asset:** `02_ticket_relabel_core_main.png`

**Speaker notes:** These look the same. The clone calls the Core fare "Main". It also has a Fare rules button that does nothing and a missing nav link. An agent trained here learns a site that doesn't exist.

## 3. How it works
- Four independent checks: visual, elements, behaviour, flows
- Every difference becomes a ticket with severity and screenshots
- About 18 seconds per audit

**Asset:** `01_architecture.png`

**Speaker notes:**
- Visual compares screenshots and ignores shifts of a few pixels.
- Elements matches every link, button and field by role, name and position.
- Behaviour clicks each control on both sites, including select options and dialog buttons.
- Flows replays whole tasks, like booking up to the Pay button, which it never clicks.

## 9. The single number doesn't predict agent success
- Two scripted agents, 14 tasks, trained on clones, tested on the real site
- On tasks independent of the audit's flows: ρ ≈ 0.1–0.3, not significant

**Asset:** `07_correlation_noflow.png`

**Speaker notes:** This is the result I'd most like challenged. Scores range widely but success barely moves. Every 95% interval includes zero (`docs/AGENT_CORRELATION.md`).

## 10. Why
- Most defects are off the task's path: 19 of 315 pairs on the path
- Agents succeed 93–95% of the time anyway
- When a defect is on the path, the task fails in 16 of 19 pairs

**Asset:** none (text slide; numbers from `docs/CORRELATION_DIAGNOSIS.md`)

**Speaker notes:** The information is there, but per defect. Averaging every difference into one number throws away *which* task it breaks. That's why the report calls it an audit-coverage summary.

## 11. What works: read the tickets per task
- Record once what each task clicks and fills on the real site
- Predict failure if a serious ticket is on one of those elements
- Held-out F1 0.91 [0.79, 0.98] (n = 22) and 1.00 (n = 14; recall CI 0.77–1.00), against about 0.1 for the score

**Asset:** `08_f1_vs_baselines.png`

**Speaker notes:**
- I wrote the rule before the diagnosis, developed it on the original clones only, and froze it in git before the held-out run.
- The two baselines use the clone-level score or severity: a score threshold scores 0.08 / 0.10, any high ticket 0.17 / 0.16.
- The claim: specific tickets predict specific task failures.
